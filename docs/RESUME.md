# 简历与面试表述

## 一句话定位

基于 Qwen3-VL、LangGraph 和混合检索开发建材销售与技术支持多模态 RAG Agent，实现企业资料与客户异构附件的结构化解析、证据召回、原图回传、受约束工具调用和本地私有化问答。

## 简历精简版

**建材销售与技术支持多模态 RAG Agent｜Qwen3-VL、LangGraph、FastAPI、Next.js**

- 针对产品画册、检测资料、施工方案、节点图集及案例文件分散的问题，开发支持 PDF、Word、Excel、CSV、扫描件和图片的本地多模态知识助手，并通过腾讯云静态前端与 Tailscale 私网后端完成可演示部署。
- 设计保留页码、Sheet、单元格范围和原始图片的 Canonical Evidence，构建 BM25 + Qwen3-Embedding + RRF + Cross-Encoder 重排的混合 RAG，实现答案引用、证据原图回传、证据不足拒答及多文件冲突提示。
- 基于 LangGraph 实现 Model-first 受约束 Agent，由本地模型选择客户附件、企业知识库、视觉理解、普通对话及联网搜索；通过工具权限、联网配额、输入快照和 Evidence 白名单抑制误调用与幻觉。
- 使用 Qwen3-VL-8B 4-bit 本地推理，并设计 Embedding／Reranker 与生成模型的 GPU 生命周期，在 16GB 消费级显卡上完成多模态 RAG；100 题审核草案中严格 Evidence Recall@5 为 92.86%（65/70，非最终答案准确率）。

## 更偏算法岗位的版本

- 提出跨格式 Canonical Evidence 协议，将 PDF 页面、Word 段落/表格、Excel Sheet/行/单元格及视觉资产统一到稳定 Evidence ID，同时保留格式专用位置，实现解析、检索、生成和引用评测的统一接口。
- 实现 BM25 与 Qwen3-Embedding 双路召回、RRF 融合、Lexical Top-8 / Dense-only Top-4 显式候选保留及 Qwen3-Reranker 重排；增加索引内容指纹、表头—数据行绑定和答案形态加权，降低大表、产品别名和精确参数场景的漏召回。
- 构建产品图／案例图／节点图／工艺图分域视觉检索，指定产品无匹配图时拒绝用相似产品替代；通过 Input Snapshot 审计 Gold 文本与图片是否真实进入模型输入，并用 Oracle Evidence 区分检索错误和 VLM 理解错误。
- 将 Agent 的业务语义交给 Qwen3-VL Planner，代码仅执行附件优先、私有数据拒答、联网授权和工具可用性等安全约束；结合 Grounded JSON、Evidence 白名单和数值引用校验，实现可追溯回答。

## 项目最有说服力的亮点

1. **不是简单套 RAG 框架**：自行处理多格式解析、表格行语义、视觉资产、混合召回、工具规划和引用回填。
2. **错误可归因**：Canonical Evidence 与 Input Snapshot 分离，能说明到底是解析、检索、视觉选择还是模型推理出错。
3. **视觉证据是真实可用的**：返回原画册/图集图片，而不是只给一段 VLM 描述或生成图。
4. **Agent 有边界**：模型做语义决策，代码控制隐私、外部调用、额度和不可验证事实。
5. **考虑消费级部署**：8B 4-bit、GPU 模型互斥、空闲卸载、Token/像素预算和速率限制都是真实工程约束。
6. **评测不夸大**：检索率、图片可用率和答案准确率分开，草案成绩明确标注审核状态。

## 两分钟面试讲法

项目来源于真实建材销售与技术支持场景：产品参数、施工方法、节点图和项目案例散落在不同文件里，人工查找慢，而且大模型回答后很难核对。我先把 PDF、Word、Excel 和图片转换为保留来源位置的 Canonical Evidence，表格按业务行绑定表头，图片作为独立资产而不是只留 OCR。检索上使用 BM25 和 Qwen3-Embedding 双路召回，经 RRF、候选保留和 Qwen3-Reranker 重排；图片按产品、案例、节点和工艺独立召回。

在线部分使用 LangGraph：本地 Qwen3-VL Planner 判断调用客户附件、企业 RAG、视觉理解、联网搜索还是普通对话，后端只负责工具授权和隐私边界。模型最终必须引用本轮 Evidence ID，服务器再回填页码、Sheet 和原图。为适配 16GB 显卡，我让 Embedding/Reranker 与 8B 生成模型错峰使用 GPU，并保留输入快照做错误归因。目前 100 题审核草案的严格 Evidence Recall@5 为 92.86%，但我明确把它作为检索诊断而不是最终回答准确率。

## 面试追问准备

### 为什么不把全部文件直接交给模型？

上下文和显存不可控，也无法稳定引用原始位置。结构化 Evidence + 问题驱动 Snapshot 可以保留完整原文，同时只发送最相关内容。

### 为什么不用纯向量检索？

建材型号、标准号、节点名和数值参数非常依赖精确词法；向量检索则擅长口语和同义表达。双路融合更稳定，并需要防止某一路候选在融合前丢失。

### Agent 体现在哪里？

模型不只是回答，还输出工具、业务意图、检索词、视觉范围和是否联网；LangGraph 执行状态流，Guard 负责权限和失败兜底。它是有限工具 Agent，不是无边界自主执行器。

### 为什么暂时不微调？

主要瓶颈是私有文档解析、检索和可信引用，参数会更新，适合 RAG。只有在正确证据已经输入但模型仍出现稳定同类错误时，才有依据做 LoRA，而不是用微调掩盖管线问题。

## 不应夸大的内容

- 92.86% 是审核草案上的严格 Evidence Recall@5，不是最终回答准确率；
- 当前支持少量异构文件问答，不是无限规模企业网盘搜索；
- 图表没有数据标签或底层数据时只支持趋势，不能保证精确读数；
- 图片相似只产生候选，不能证明产品品牌、真伪或工程适用性。
