# 核心算法设计

本文重点说明项目的算法决策、为什么这样设计，以及它相对于“把整份文件直接塞给模型”的优势。

## 1. Evidence-first，而不是 Answer-first

系统首先建立可追溯 Evidence，再让模型回答。每条证据至少包含：稳定 ID、原始文本或视觉资产、文件来源、结构位置、解析器及置信度。模型生成后只允许引用本轮提供的 Evidence ID，服务器负责将其回填为页码、Sheet、单元格和原图。

收益：

- 可以验证回答是否真的来自企业资料；
- 可以返回节点图、案例图和产品图原件；
- 可以把解析、检索和生成错误分开统计；
- 后续更换模型时不需要重建文档协议。

## 2. 结构感知切块

### 普通文本

长段落使用有限 Token 窗口和重叠，优先在标题、段落、换行和句末边界截断。窗口保留父 Evidence ID 和真实页码，不跨不相关结构任意拼接。

### 表格

表格按业务行形成候选，并绑定紧凑表头：

```text
[TABLE sheet=Facilities]
[ROW] Property='Building A' | Primary space type='Office - General - 310'
```

这解决两种常见错误：字段名和字段值被分到不同窗口；每个单元格复制整张表头导致索引词频污染。极宽行仍需按字段组切分，但字段名和值必须作为不可分割单元。

### 图片

图片不转换成一段文本后丢弃。原图独立保存，OCR／标题／附近文字只构成检索语义；回答时仍可把原始图交给 VLM 并返回给用户。

## 3. PDF 按页分流

PDF 可能同时包含文本页、扫描页和图表页，因此逐页判断：

```text
文本层可靠 → 原生文本 + 表格解析
无文本 / 乱码 / 严重错位 → 渲染图片 → OCR + Layout + Table
文本 + 图片混合 → 原生文本与视觉资产并列保留
```

判断不只看“能否复制文字”，还检查乱码率、字符数量、阅读顺序和表格结构。扫描处理按批执行并报告 `completed / failed / pending`，只有覆盖完成才能标记整份 PDF 完成。

## 4. 混合检索

### 候选生成

- BM25：精确命中产品型号、标准号、施工节点、项目名和数值单位；
- Dense：处理同义词、口语化问题和跨措辞匹配；
- 产品别名扩展：只扩展经业务确认的等价关系，不修改原文名称。

### RRF 融合

使用 Reciprocal Rank Fusion：

```text
RRF(d) = Σ 1 / (k + rank_i(d))
```

RRF 不依赖不同召回器的原始分数同尺度，但仅靠 RRF 仍可能让一条召回流挤掉另一条流的关键候选。因此融合池显式保留：

- Lexical Top-8；
- Dense-only Top-4；
- 其余位置再由 RRF 补齐。

视觉候选也分别保留词法和向量入口，不通过最终融合分数反推候选来源。

### Cross-Encoder 重排

对候选使用本地 Qwen3-Reranker 计算问题—证据相关性。随后只做小幅、可解释的领域校正：

- 施工步骤题优先完整工序序列；
- 数值测量题优先包含测量方法与单位的证据；
- 材料构成题优先包含原料、成型和构成关系的证据；
- 案例题优先结构化案例，而不是普通产品描述。

规则只调整候选排序，不生成业务事实。

## 5. 索引一致性

Lexical 与 Dense 索引记录同一份规范化 Evidence 的 SHA 指纹。加载时校验：

- 文档数量；
- Evidence ID 顺序；
- 内容指纹；
- Embedding 维度与矩阵行数。

任一不一致就禁用该 Dense 快照，而不是把不同版本的证据静默混合。

## 6. 问题驱动的视觉召回

视觉排序综合：问题词与图片标题/OCR/附近文字的重合、已召回文本所在页、视觉类别、产品名称或别名、项目案例结构信息。

产品图片使用独立审核图库：

```text
Planner: wants_visuals=true, visual_scope=product
→ 检索完整审核产品图库
→ 精确产品/别名匹配
→ 返回对应原图
```

若指定产品没有审核图片，则返回空集，不用其他花色或产品代替。产品总览请求可返回少量代表图，但不能把它们误标为某个未匹配产品。

Excel 原生图表若存在源单元格，精确数值来自工作簿单元格；PDF 图片图表只有可见数据标签时才允许提取精确值，否则只回答趋势。

## 7. Model-first Tool Planner

Planner 在一次本地生成中同时决定：

- 工具集合；
- 业务 intent 与 task type；
- 保留命名实体和约束的 retrieval query；
- 案例筛选条件；
- 是否为产品总览；
- 是否需要知识库图片及 visual scope；
- 是否确实需要公开网页搜索。

后端 Guard 不再重复做一套大型关键词业务分类，只执行确定性边界：工具可用性、外部调用授权、附件优先、动态私有数据拒答和失败兜底。

这个设计兼顾语义泛化与工程安全：模型能理解“详细介绍一下”“给我看看它的图片”等上下文指代；代码仍控制隐私、费用和不可用工具。

## 8. 多文件证据选择

客户附件的 Canonical Evidence 完整保留。问题到来后：

1. 对每份文件内部的窗口打分；
2. 只给真正相关的文件最低上下文配额；
3. 所有高分窗口竞争剩余 Token；
4. 去除同一表格或页面的近重复窗口；
5. 选择与高分证据对应的图片；
6. 将实际输入冻结为 Input Snapshot。

模型最终可选择一份或多份支持文件，并输出 `redundant / complementary / conflicting / none`。如果正确证据未进入 Snapshot，端到端应算失败，但模型能力分析应归因于解析或召回。

## 9. 联网来源排序

网页检索不是简单展示搜索引擎前五条。结果经过：

- URL 规范化与去重；
- 查询词相关性；
- 按问题类型配置的来源域名权威性；
- 时效性；
- 对少量高价值页面的 robots 检查、受限下载和正文片段验证。

采用本地缓存与每日额度预留，避免普通聊天浪费有限 API 次数。即使联网开关开启，“你好”也不会触发搜索。

## 10. Grounded 输出校验

模型输出 JSON 后依次验证：

1. Schema 合法；
2. Evidence ID 存在于本轮白名单；
3. 关键结论至少有一条支持证据；
4. 数值能在引用证据中验证；
5. 冲突没有被静默合并；
6. 证据不足时执行拒答；
7. 视觉候选未被提升为未经证实的品牌或性能结论。

失败时返回带缺失信息和下一步的安全结果，而不是暴露原始模型错误文本。

## 11. 16GB GPU 共存

Qwen3-VL-8B 采用 4-bit NF4。Embedding 和 Reranker 在生成模型加载前迁移到 CPU；生成完成后可恢复。Batch Size 固定为 1，并控制视觉像素、图片数、上下文和输出长度。默认空闲 600 秒卸载生成模型。

`torch.cuda.empty_cache()` 只释放无引用缓存，因此代码同时删除输入、输出和临时张量，避免把 GPU Tensor 放入长期结果列表。

## 12. 为什么当前以 RAG/Agent 为主而非微调

项目的主要难点是私有资料解析、证据召回、工具选择、图片回传和可信性，而不是让模型记住企业参数。企业资料会更新，适合进入 RAG；确定性聚合和校验适合由代码完成。

只有在冻结评测后仍能确认以下稳定误差，才值得微调：结构化输出持续不稳定、相同证据下模型经常拒答、工具语义计划系统性错误或特定视觉任务明显不足。否则优先修复解析、索引和召回，避免用 LoRA 掩盖管线问题。
